Assignment 2 — Distributed Banking Platform

Sharding, replication and two-phase commit  |  Technical report
Django/DRF bank shards · FastAPI shard-aware gateway · PostgreSQL 16 · Docker Compose

The system implements a two-shard banking platform in which a client talks only to one gateway. The gateway resolves every account through a range shard map, load-balances over healthy replicas of the owning shard, and runs cross-shard transfers through a two-phase-commit (2PC) coordinator whose durable decisions live in an independent database. Same-shard transfers stay inside one PostgreSQL transaction. The report explains each requirement and maps it to the implementation and to the test evidence.

Result summary. Client acceptance suite: 16/16 requirements demonstrated. Non-interactive experiment harness (Experiments 5, 6 and 7): 36/36 checks passed. Concurrent test: 60 cross-shard and 40 same-shard transfers, all completed, money conserved, 0 unresolved coordinator rows and 0 prepared transactions left behind. The DRF browsable API is available on the replica ports (8001–8004) for inspection; the banking client still uses only 8000.

2. Architecture and request path

Figure 1 — Deployment and control/data paths.

Component responsibilities

  • Client (client test/client.py): performs balance, deposit, withdraw and transfer calls against BASE_ROOT=http://host:8000. It does not import the shard map, does not query both shards, and cannot choose a replica. The transfer helper adds a unique request_id and an X-Request-ID header.
  • Gateway (gateway/main.py, balancer.py, coordinator.py): validates transfer payloads (positive amount, at most two decimals, different accounts, request-ID syntax), resolves the shard, selects a healthy replica, proxies local operations, and hosts the 2PC coordinator. It is the only component that knows the topology.
  • Shard replicas (transactions/): Django/DRF applications. They own the account and participant-commit models, expose the public account API and internal /internal/2pc/* endpoints, enforce ownership on the write path, and log the replica ID in every response header and structured log line.
  • Coordinator store: a PostgreSQL database used only for the transaction state machine. It is deliberately not in either shard database, so a shard outage cannot erase a recorded decision.

3. Sharding, routing and load balancing

3.1 Deterministic range shard map

Partitioning is range-based. config/shard_map.yaml is the single topology source and states the ranges explicitly:

version: 1
epoch: 1
ranges:
  - start: A0001
    end: A1000
    shard_id: shard-a
  - start: A1001
    end: A2000
    shard_id: shard-b

Account identifiers have the form A plus four digits, so lexicographic comparison is also numeric comparison. The map loader validates the format, rejects inverted or overlapping ranges, and rejects gaps between adjacent ranges; the gateway's loader also requires every shard named by a range to have at least one replica. The same map is loaded by each shard at startup: transactions/sharding.py checks that this process's SHARD_ID owns at least one range and fails fast otherwise. This prevents a misconfigured replica from serving accounts it does not own.

Each account has exactly one authoritative shard. The full dataset is not copied to both shards: banking_a contains only A0001–A1000 and banking_b only A1001–A2000. A request for A0500 is always routed to shard A; A1500 is always routed to shard B. The gateway refuses account listings through /api/accounts/ so that no code path accidentally performs a global scatter-gather balance query.

3.2 Routing and replica selection

  1. The gateway reads the account number from the URL or transfer payload and calls shard_for(account). If no range matches, it returns 404 UNKNOWN_ACCOUNT without contacting any shard.
  2. Within the owning shard, select(shard_id) walks the healthy replica list in round-robin order. An unhealthy replica is never selected while a healthy one exists; an optional exclusion set lets a retry avoid the replica that just failed.
  3. For reads, the gateway may retry once on a transport error with the next healthy replica. For writes it does not blindly retry, because a lost response has an uncertain outcome. Transfers instead carry an idempotent request_id, and the status API can be polled.
  4. Every response carries X-Served-By, X-Shard and X-Request-ID. The shard log records the replica, account, action, result, balance and latency; the gateway log records the chosen shard and replica.

3.3 Health detection and failover

Each replica exposes GET /health; the gateway probes all replicas every 2 seconds with a 1-second timeout. Two consecutive failures mark a replica unhealthy; three consecutive successes bring it back. A shard is considered available while at least one of its replicas is healthy. These thresholds are configuration values (config/gateway.yaml), not hard-coded in the request path.

Load-distribution check. Twelve sequential balance reads for A1001 (shard B) were served by shard-b-1 6 times and shard-b-2 6 times. Twelve reads for A0501 (shard A) were split 6/6 between shard-a-1 and shard-a-2. No request for a shard-A account was served by a shard-B replica.
Failover check. With api-b1 stopped, twelve reads for A1001 were all served by shard-b-2; shard-A traffic continued to be split across its two replicas. After api-b1 was restarted it rejoined the pool.

4. Concurrency control and banking operations

4.1 Replica consistency

Replicas are stateless with respect to balances: they do not cache balances and they do not keep independent copies. Every read and write goes to the shard database, which is the authority. A write executes inside transaction.atomic() and begins with SELECT ... FOR UPDATE (select_for_update()), so concurrent operations through different replicas serialize on the same row. This prevents lost updates even when both replicas process requests for the same account at the same time. The database also enforces CHECK (balance >= 0); the application checks the balance before a withdrawal so that the common case returns a useful 422 instead of a constraint error.

4.2 Local operations and same-shard transfers

OperationTransaction scopeGuarantee
Balance inquirySingle shard, read-onlyReads the authoritative row; no cross-shard aggregation.
Deposit / withdrawOne database transaction on the owning shardRow lock, atomic update, non-negative balance constraint, durable commit before the response.
Same-shard transferOne database transaction on the owning shardBoth rows are locked in ascending account order, then both balances are updated. Either both updates commit or neither does. No coordinator is involved.
Cross-shard transferTwo participant transactions coordinated by 2PCEach shard prepares its own row change; the durable decision is recorded before commit or abort is sent; see Section 5.

Sorting the two account numbers before locking is a small but important detail: two opposite-direction same-shard transfers cannot each hold one row and wait for the other. The same global ascending order is used by the coordinator when it prepares the two shards, so the cross-shard case has the same deadlock-avoidance property.

4.3 Participant transactions

A 2PC participant cannot use transaction.atomic() because Django commits on block exit, while the protocol needs a prepared-but-not-committed state. transactions/participant.py therefore opens a short-lived psycopg2 connection in autocommit mode, issues BEGIN, sets lock_timeout and statement_timeout, locks the account row FOR UPDATE, validates funds and ownership, applies the tentative update, and executes PREPARE TRANSACTION '<txid>:<shard>'. PostgreSQL's pg_prepared_xacts is the authoritative PREPARED state. The participant does not resolve prepared transactions on startup; recovery belongs to the coordinator.

The prepare timeouts are 4 seconds for lock acquisition and 5 seconds for the whole statement, both below the coordinator's 6-second RPC timeout. A participant that cannot acquire a hot row in time votes NO with LOCK_TIMEOUT or PREPARE_TIMEOUT. This bound is part of the correctness argument: once the coordinator's RPC attempt has ended, no prepare can still be running and later create an orphaned prepared transaction.

4.4 Admission control and log hygiene

Each shard process enforces MAX_CONCURRENT_CLIENTS=20 with a process-local counter in the logging middleware; excess requests receive 503 immediately. The middleware logs only /api/ requests, so health probes and static files do not flood the transaction log. Gunicorn uses one gthread worker with 48 threads; the pool is deliberately larger than the admission limit. During testing, a 12-thread pool allowed blocked prepares on a hot account to occupy every thread, delaying the commit that would release the row lock and producing avoidable lock timeouts. With 48 threads the commit path always has capacity, and the concurrent experiment passes. The gateway also disables Uvicorn access logs; its structured request/coordinator logs are the useful operational record.

5. Two-phase commit

5.1 Protocol

The gateway determines the source and destination shards from the shard map. If they differ, it calls the coordinator with the accounts, amount, shards, txid and optional request_id. The coordinator inserts an INITIATED row, moves to PREPARING, and prepares one participant per shard.

  • Phase 1 — prepare. Participants are sorted by account number and prepared in that global order. Each participant validates ownership, amount and funds, locks its account row, applies the tentative update, runs PREPARE TRANSACTION, and votes YES or NO. A NO or an indeterminate outcome leads to abort.
  • Durable decision. If and only if every participant voted YES, the coordinator writes COMMIT_DECIDED with decision COMMIT to coord-db before sending any phase-2 message. Otherwise it writes ABORT_DECIDED with decision ABORT. The schema's check constraints make an inconsistent state/decision pair unrepresentable.
  • Phase 2 — commit or abort. The coordinator sends COMMIT PREPARED or ROLLBACK PREPARED to every prepared participant; commits are issued concurrently. Participants are idempotent: a repeated COMMIT for an already committed GID is a no-op, and a ParticipantCommit marker prevents a later rollback from undoing a recorded commit.
  • Completion. The transaction becomes COMPLETED only after every participant acknowledges. If an acknowledgement is missing, the row stays in COMMIT_DECIDED and recovery retries; the gateway never reports success early.
Figure 2 — Successful cross-shard transfer. Commits are issued concurrently; they are drawn sequentially for readability.

5.2 Idempotency and repeated messages

Every cross-shard transfer has a coordinator-generated 32-hex-character txid. If the client supplies a request_id, it is stored in a UNIQUE column. A retry with the same request_id and the same accounts/amount returns the existing transaction; the same request_id with different details returns 409 REQUEST_ID_CONFLICT. On the participant side, COMMIT PREPARED is retried safely because the participant first checks pg_prepared_xacts and the ParticipantCommit marker. A rollback after a recorded commit is refused rather than silently destroying a committed effect.

6. Durable state and recovery

6.1 Persistent states

StateDurable meaningAllowed next steps
INITIATEDRow created; no participant contactedPREPARING, or abort if recovery finds a stale initiated transaction.
PREPARINGAt least one PREPARE has been sentPREPARED if all vote YES; ABORT_DECIDED on a NO or timeout; recovery may abort after the grace period.
PREPAREDAll participants voted YES, but no decision is durable yetCOMMIT_DECIDED if the coordinator is still deciding; recovery aborts a fully prepared transaction that has no durable decision.
COMMIT_DECIDEDDurable COMMIT decision; phase 2 may be incompleteCOMPLETED only after every participant acknowledges. Recovery retries COMMIT; it never converts to ABORT.
ABORT_DECIDEDDurable ABORT decisionROLLBACK PREPARED on all prepared participants, then ABORTED.
COMPLETED / ABORTEDTerminal stateNo further state changes.

The coordinator table has a primary key on txid, a unique request_id, a partial index over non-terminal states, and check constraints that tie each state to its decision. The decision and the state are written in one row update, so there is no window in which the database contains a COMMIT decision with an ABORT state (or the reverse).

6.2 Recovery loop

The coordinator runs a recovery sweep every 5 seconds. It selects up to 50 non-terminal rows, takes a per-transaction lock so the request path and recovery cannot race, and calls the same state machine with wait=False. The handling depends on the durable point reached:

  • INITIATED or PREPARING older than the 12-second grace period → abort without preparing, recording RECOVERED_INITIATED or RECOVERED_PREPARING.
  • PREPARED with no decision → abort, recording RECOVERED_UNDECIDED. A prepared transaction that never reached a durable COMMIT is not committed.
  • COMMIT_DECIDED → resend COMMIT to every participant; mark COMPLETED when acknowledged. The decision is immutable.
  • ABORT_DECIDED → resend ROLLBACK; mark ABORTED when acknowledged.

6.3 Required recovery scenarios

CaseSituationObserved / implemented behavior
AOne shard votes YES, the other rejects (for example insufficient funds).Coordinator records ABORT_DECIDED and sends ROLLBACK PREPARED to every participant that prepared. No balance changes. The client receives 422 ABORTED and the txid can be queried.
BAll participants prepared; coordinator stops before acknowledging phase 2.On restart, the unresolved row is read from coord-db. The committed test pauses after the durable decision, stops the gateway, verifies both prepared transactions survive, then restarts; recovery completes the transaction. If the crash had occurred before a decision, recovery would abort safely.
CCOMMIT is recorded, but not all participants acknowledged.Recovery sees COMMIT_DECIDED and retries COMMIT. It never replaces the decision with ABORT because a participant is temporarily down. Repeated COMMIT is harmless; the participant commit marker and prepared-xact check make the effect exactly once.

8. Limitations and deliberate scope

  • Single gateway process. The gateway is a single container and therefore a single point of failure. The assignment requires a shard-aware gateway, not a highly available gateway; the coordinator is logically separate but shares the process.
  • Blocking 2PC. Prepared participants hold row locks until the decision is applied. A hot account can make other prepares wait; the bounded lock/statement timeouts convert that into a safe NO vote, and the client can retry with the same request_id. This is correct but not a high-throughput protocol.
  • Static topology. The shard map is a mounted YAML file with epoch: 1. Changing ranges requires a configuration update and restart; there is no online re-sharding, change capture, epoch fencing or migration state machine. Bonus I is intentionally not implemented.
  • No database replication. Each shard has one PostgreSQL instance; only the application replicas are replicated. Database replication and failover were explicitly not required.
  • No self-healing controller. Replica restart is an operator action (docker compose restart); the gateway only detects health and routes around a failed replica. Bonus II is intentionally not implemented.
  • Demo security. Credentials are local demo values; there is no authentication, authorization or TLS. The DRF browsable API is exposed on host ports for inspection only.
  • Operational limits. max_prepared_transactions=64 bounds concurrent prepared transactions; the prepared state is durable but not monitored by an alert. Write requests are not automatically retried after a transport failure because the outcome is uncertain; the transaction-status API is the recovery tool.
